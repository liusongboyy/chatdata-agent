# 建模覆盖度：问数准确率的最大杠杆

**一句话结论**：在本项目里，提升问数准确率最有效的手段是**把缺失的建模形态补齐**，
不是换模型、不是调 prompt、也不是加列描述。

依据：2026-10-26 的一次对照测量——保险域基线的 66 条用例里，
**只改评测夹具的三条列定义、代码一行未改**，通过率从 74.2% 升到 83.3%。

## 一、那次测量到底是什么

补齐的三条登记：

| 补什么 | 原来缺了会怎样 |
|---|---|
| `province` → `COUNT_DISTINCT`「省份数」 | 问「一共涉及多少个省份」，模型只能**逐项列出每个省** |
| `premium` → `AVG`「平均保费」 | 问「平均每张保单的保费」，模型出 `SUM` + `COUNT` 两列，让用户自己除 |
| `term_years` 另加一条**不聚合**的「保障年限」 | 问「保障年限为 10 年的保单」，只有 `AVG` 那条，没法当筛选条件 |

三条都转 PASS。两次跑分 83.3% / 81.8%（此前 74.2%），涨幅远超 ±3pp 的模型波动。

## 二、为什么这件事这么要紧

### 2.1 失败是静默的

缺了对应指标，模型**不会报错**，它会拿手上的东西凑：

```sql
-- 问「一共涉及多少个省份」
-- gold:
SELECT COUNT(DISTINCT province) FROM ins_policy
-- 模型实际给的（因为没有「省份数」这个指标）：
SELECT province, COUNT(policy_no) FROM ins_policy GROUP BY province
```

后者语法合法、执行成功、返回真实数据——只是**答的不是用户问的那个问题**。
用户看到一张省份明细表，多半以为「哦原来要这样看」，而不是「它理解错了」。

这正是本项目反复处理的同一类失败：**不报错的错**。

### 2.2 对照：列描述画像投入了同样的精力，收益为零

同期还做了一个业界公认高性价比的改动——给列生成描述与取值样例注入 prompt
（BIRD 企业级研究：无列注释 66.5% → 有注释 73.8%）。实测结果：

| 条件 | 保险域（多次） |
|---|---|
| 有描述 | 75.8% / 74.2% / 74.2% / 75.8% |
| 无描述（对照） | 74.2% |

**没有可测量的提升。** 原因是本项目的评测域已经配了术语：

```
ask_term 已有：保单状态 → 取值：生效、已过期、退保（中文，与库内一致）
画像生成的是：保单状态（varchar），取值 已过期、生效、退保，共 3 种
```

后者信息量反而更低——它没说"中文，与库内一致"，而那正是模型最容易搞错的地方。

**这两件事放在一起才说明问题**：同样的投入，一个 +9pp、一个 +0。
差别不在"信息量"，而在**那个域有没有对应的表达形态**。

## 三、覆盖度检查工具

经验做成了可执行的检查：`ModelingCoverageCheck`，管理员建完域当场能跑。

```
GET /api/engine/admin/domains/{id}/modeling-check
```

四类提示，**全部 WARNING，不阻断启动**：

| 检查 | 提示什么 |
|---|---|
| 聚合覆盖 | 有数值列却没有任何 `AVG`；有分类列却没有任何 `COUNT_DISTINCT` |
| 指标/维度双登记 | 像"离散量"的数值列（年限/年龄/优先级）只有指标、没有维度 |
| 时间口径 | 多个日期列，但没有任何 `apply_kind=time` 的术语 |
| 自相矛盾 | 统计条件引用了它自己（循环定义，条件恒真或恒假） |

### 3.1 为什么是 WARNING

一个只用来查总额的域，配不配 `AVG` 都无所谓。把它做成 ERROR 会让"多配一层"
变成"启不来"，代价与收益不成比例。

### 3.2 为什么不接进启动校验

`EngineConfigValidator` 回答「这个域**能不能用**」，覆盖度回答「**配得够不够好**」。
混在一起有两个后果，都实测过：

1. 10 个既有测试夹具（最小化的域）全部多出警告，测试失去信号
2. 管理员看到「缺 AVG」会以为域有问题，实际上它跑得好好的

两件事分开：**能用的判据必须硬，够不够好的判据只能说**。

### 3.3 提示的收窄

第一版对**所有**数值指标报"缺维度"，结果每个金额列都被点名：

```
「订单表」里的列「amount」只登记了指标，没有对应的维度……   ← 金额列永远不需要
「订单表」里的列「premium」只登记了指标，没有对应的维度……  ← 同上
```

一个天天喊"你缺维度"的检查，很快没人会看。现在只对**列名像离散量**的提示
（`year/age/level/priority/count/qty/次数/年限/年龄/等级…`）——
金额、数量这类连续值几乎不会被当成筛选条件。

**宁可漏报，也不要制造噪音。**

## 四、新建域时的检查清单

按重要性排序，都是"不配不会报错，只会答案形态不对"：

1. **每种度量的聚合形态配齐了吗**
   - 金额/数量：至少一条 `SUM`、一条 `AVG`
   - 分类字段：至少一条 `COUNT_DISTINCT`（"有多少种"是最高频的问题之一）
2. **会被当条件的数值字段，有没有双登记**
   - 同一个 `col` 配两行：一行带聚合（指标），一行不带（维度）
   - 「保障年限为 10 年」需要后者
3. **每个日期列都用术语声明了吗**
   - 域里有 2 个以上日期列时必须有，否则引擎按别名猜，一律落到第一个——
     「按报案日期查」拿回的是生效日期那段时间的数据
4. **派生指标与条件指标的输入名称核对过吗**
   - 启动校验会检查，但建完域就跑一遍更快
5. **列描述与取值样例**（优先级最低）
   - 已经有术语覆盖的域，收益接近零
   - 全新的、没有术语的域值得跑一次画像

## 五、反面清单：这些没带来提升

记录下来，免得以后有人重做一遍：

| 尝试 | 结果 | 原因 |
|---|---|---|
| 列描述 + 取值样例注入 prompt | +0 | 被测域已配术语，已覆盖同等信息 |
| 模板拼装的描述（"保费（decimal），如 313.79"） | +0 | 信息量低于已有术语 |

**那要让它有效，得做什么**：用模型把画像写成**业务描述**（而不是模板拼装），
并且**只对没有术语覆盖的字段生成**，避免与术语重复。
