# 渠道独立成进程，用自定义 grant 代表用户

## 背景

问数原本只有浏览器入口：浏览器 → 网关（BFF）→ ask，身份由 IAM 的授权码流程建立，
ask 内省令牌拿到角色与组织。

要接飞书之后，出现一个此前不存在的问题：**飞书消息带的是 `open_id`，ask 不认**。
需要把「飞书说这个人是谁」换成「IAM 说这个人是谁」，而且换出来的东西必须让
ask 的行级规则照常生效——否则渠道要么看得到全部数据，要么什么都看不到。

同时有三个约束：

1. 渠道的入站流量来自飞书，不是浏览器
2. 飞书要求事件在 3 秒内响应，而问数要 5–15 秒
3. 群聊里任何人都会看到机器人发出的结果

## 决定

### 一、渠道独立成进程，不塞进网关

`chatdata-channel`（端口 20000），不经过网关。

网关是**给浏览器**的：它的安全配置围绕会话 Cookie、CSRF、BFF 授权码流程展开。
把飞书的事件塞进去，等于让「给浏览器鉴权」的那套去处理飞书的签名请求，两边都不自然。

独立进程还带来两个实际好处：公网只需放行 `/channel/feishu/event` 一个路径；
渠道故障不影响 Web 问数。

### 二、身份用自定义 grant，不用内置的 RFC 8693

Spring Authorization Server 7.1.0 内置了 Token Exchange，但它的第一步是
`findByToken(subject_token)`——要求 `subject_token` 是**已存在于库里**的令牌。
而飞书用户可能从没登录过 Web 端，库里没有他的令牌可换。

绕过它只能自己伪造一张 subject_token，那比直接写一个 grant 更复杂，
还会在 `oauth2_authorization` 里留下一张不该存在的令牌。

所以注册 `urn:chatdata:params:oauth:grant-type:channel`，请求带
`channel` + `channel_user`，IAM 校验后签发一张 REFERENCE 令牌。

**三道校验，缺一不可：**

| 校验 | 不做的后果 |
|---|---|
| 客户端必须是配置里的 `channel-bot` | 任何客户端注册时声明这个 grant 就能用 |
| 目标用户绑定了本渠道（反查 `external_id`） | 一个泄露的 secret 就是能冒充任何人的万能钥匙 |
| 目标用户是启用的 | 产生无意义的授权记录，且错误信息误导 |

### 三、渠道不判断权限

渠道只做「哪个用户问了什么 → 拿他的令牌去问 → 把结果排版回去」。
行级规则、列脱敏、角色判定全在 ask 里。

这条边界是硬的。一旦渠道开始判断「这个人能不能查」，就出现了**第二个权限判定点**，
而它看起来像是「顺手加的便利」——这类腐化最难在 code review 里发现。

### 四、传输选 webhook，不选长连接

飞书两种方式都支持，长连接甚至不需要公网地址。选 webhook 的理由是**线上形态**：

- 多实例可正常负载均衡（长连接是集群模式，随机投给一个实例）
- 每个事件是一个 HTTP 请求，能被日志/APM 统一观测
- 失败会重推 4 次（15s / 5min / 1h / 6h），长连接断线期间是静默丢失

代价是本地开发要内网穿透，且验签与解密要自己做。

### 五、群聊里直接回复，接受「群里发言即公开」

张三在群里问「上周订单金额」，卡片发到群里后**全群可见**，包括权限比他小的人。

这不是缺陷，是 IM 的固有语义。接受它需要满足：群里的人本来就该看到同样的数据；
不在跨权限的群里用问数。**跨权限的群应该把机器人移出去**，而不是靠代码兜底——
代码无法知道「这个群里的人该不该互相看到数据」。

配套约束：群聊里按发言人隔离会话（`chat_key = chat_id:open_id`），
否则李四的追问会接上张三的上下文，而那条上下文里有张三权限下的数据。

## 考虑过的其他方案

- **让 ask 信任 `X-Channel-User` 头**：绕过 OAuth 体系，等于开后门，
  审计上「谁问的」变成「谁声称是谁」。否决。
- **channel 自己查 IAM 用户、组装 PermissionContext 传给 ask 的内部端点**：
  在 ask 上开第二个入口，两套鉴权逻辑要同步维护——最容易长出漏洞。
- **现在抽 `ChannelInbound` 接口，为钉钉/企微预留**：三个实现都没有时抽出的
  接口是「想象中的共性」。飞书 webhook、钉钉 Stream 模式、企微只有 webhook，
  传输层差异比想象大；卡片模型（飞书卡片 / 钉钉 ActionCard / 企微 markdown）
  更是无法统一。等第二个实现进来再抽。

## 后果

- **渠道成为第二个"能签发令牌"的地方**（严格说是触发签发）。IAM 的 channel 客户端
  密钥一旦泄露，攻击者能冒充**已绑定**的用户——所以绑定校验不能省，
  且密钥不设默认值、缺失时启动失败。
- **`channel_answer` 会存完整结果行**（最多 1000 行/条）。需要清理任务，
  否则表会随使用量单调增长。
- **3 秒约束把入站处理劈成两段**：webhook 线程只做验签/解密/去重/入队，
  问数在工作线程。但**卡片回调必须同步**——响应体决定客户端行为，
  异步了就只能"先弹 toast 再延时更新"，多一条链路和它的失败态。
- **飞书卡片 schema 的坑无法用单测覆盖**（`note` 组件在 2.0 被废弃、
  加密事件里 `type` 在密文内）。这类问题只能靠真机联调发现，
  所以接新渠道时**必须真的发消息验证**，不能只看测试绿。
