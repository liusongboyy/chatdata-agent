# 角色模型：`chat2bi` 是管理台角色，不是问数角色

## 背景

第三方 BI 产品 用同一个角色名 `chat2bi` 承担了两件被我们混为一谈的事。最初的判断是
「`chat2bi` 是必需角色，否则问数接口会 403」——**该判断是错的**，它来自一次越界推断：
看到 `第三方助手控制器./savePerm` 上有 `@RequiresRoles({"chat2bi","admin"})`，
就把它推广成了「问数接口需要 `chat2bi`」。实际上 `第三方问数控制器` **没有任何角色注解**。

这个错误判断的直接后果是：所有用户都被授予了 `chat2bi`，于是**每个能问数的人都能进入管理台，
配置数据源、语义域与指标口径**。

## 决定

**`chat2bi` 只授予管理员。** 问数能力与数据权限**完全不依赖它**。

实测判据（服务端渲染管理台时计算）：

| 用户 | 角色 | `canConfig` | 管理台页面 |
|---|---|---|---|
| `admin` | chat2bi | **true** | 84 KB |
| `zhangsan` | 区域经理 | false | 20 KB（登录页） |
| `wangwu` | 区域经理 | false | 20 KB（登录页） |

摘掉 `chat2bi` 后复测：zhangsan 仍能正常问数（`rows=1`，行级规则照常生效），
但配置接口被拒（`"没有权限，请联系管理员分配角色！"`）。**两个层面都拦住了**——
界面 `canConfig=false`，接口层角色校验拒绝，绕过界面直接构造请求同样无效。

## 三种角色的职责划分

| 类别 | 角色 | 决定什么 | 授予给谁 |
|---|---|---|---|
| **管理台** | `chat2bi`（厂商契约名，不可改） | 能否进入管理台配置数据源 / 语义域 / 数据表 / 助手 | **仅管理员** |
| **数据权限** | `区域经理` / `分析师` / … | 能看哪些行、哪些列 | 按业务需要 |
| **功能开关** | 如未来的 `auditor` | 与数据无关的功能 | 按需 |

数据权限角色必须与语义域 `perm_json` 中的配置**逐字符一致**：
`rowRules[].role`、`colRules[].role`、`grantRoles`，以及助手 `perm_json.grantRoles`。

## 考虑过的其他方案

- **保留 `chat2bi` 给所有人，改用 `@RequiresPermissions` 区分**：需要自行维护一套功能权限码
  （`jimu:chat2bi:permEdit` 等），而厂商的权限判据与角色判据是**两个独立开关**，
  维护两套的一致性成本高于直接用角色区分。
- **不区分，接受业务用户可配置**：等于让被权限约束的人可以修改约束自己的规则，
  与「数据权限是第一优先」直接冲突。

## 后果

- ~~**`sql/02-role-seed.sql` 中的清理语句不可删除。**~~ 该脚本随 `sys_role` 退役一并删除
  （2026-10-22，角色改由 IAM 管理，见 `.scratch/iam-platform/spec.md`）。它当初清掉的
  错误 `chat2bi` 授权属于旧 `sys_role` 数据；迁移前若未跑过它，需要单独确认。
- **角色来源已改**：角色码以 IAM 的 `iam_role.code` 为准，`sys_role` / `sys_user_role` 不再被读取。
- **`DevLoginController` 按角色分流落点**：有 `chat2bi` 进 `/jimu/chat2bi/index`（管理台），
  否则进 `/jimu/chat2bi/chat`（嵌入版聊天）。这不是为了好看——实测中无该角色的用户
  访问管理台入口会被打回登录页，而聊天入口对他们可用。
- **`canPermEdit` 实测对所有角色均为 `false`。** 即权限规则（`rowRules` / `colRules`）
  本身的编辑界面默认关闭。这意味着**语义域的管理者无法通过界面修改数据权限规则**——
  规则目前只能由我们直接改 `perm_json`。若将来需要让管理员自助配置数据权限，
  需要先查清 `canPermEdit` 的开启条件。
- **新增任何角色前，先确认它属于哪一类。** 把数据权限角色误当管理台角色（或反之）
  是这个系统里最容易犯、也最难在运行时发现的错误——它的失败形态是静默的。
