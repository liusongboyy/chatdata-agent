# 集中身份、分布授权：数据权限归业务模块，IAM 只做身份与准入

## 背景

IAM 平台最初按「权限的事实来源必须只有一处」的直觉，把数据域/助理的
行级、列级策略也收进了 `iam_policy`：ask 启动时通过 `PolicyProvider` 从 IAM
取策略文档，引擎负责解释与执行。

在单模块阶段这能工作，但进入**多服务器模块开发**后，问题开始显现：

1. **领域知识渗进 IAM。** `iam_policy` 虽然声称存"不透明 JSON"，但 IAM 管理台
   必须知道 `DOMAIN` 与 `ASSISTANT` 两套文档结构，才能提供编辑界面。ask 每新增
   一个操作符、动态变量或规则类型，IAM 都可能要跟着改界面、发版。
2. **资源元数据跨服务。** 策略页要显示数据域/助理名称、要给出字段下拉，就得读
   ask 的库或 ask 的管理接口；IAM 的部署、权限与故障域因此被拉长。
3. **资源生命周期割裂。** 域/助理在 ask 创建与删除，策略却存在 IAM；删除资源后
   策略变成孤儿，IAM 也不知道资源是否还存在。
4. **编辑入口与操作路径打架。** 管理员在 ask 配完数据域，还要跳到 IAM 配它的数据
   策略；而 ask 里原有的 `perm_json` 表单仍在，形成两个看起来都能改的入口。
5. **新模块无法复用。** 如果每个业务模块的行/列权限都要进 IAM，IAM 会逐渐变成
   "所有模块的配置中心"，与它作为基础身份模块的定位背离。

现有代码其实已经具备另一条路径：`ask_domain.perm_json` / `ask_assistant.perm_json`
是引擎原本的本地策略来源，`policy.source=local` 开关也保留着。说明"策略归模块"
不是推倒重来，而是把已有能力扶正。

## 决定

### 1. 权限分成四层，各归其位

| 层次 | 归属 | 回答的问题 | 示例 |
|---|---|---|---|
| 身份 | IAM | 你是谁 | 用户、组织、登录、令牌 |
| 功能权限 / 模块入口 | IAM | 你能进哪个模块、打开哪个页面 | `ask.read` scope、`ask.admin.domains` |
| 资源授权 | 业务模块 | 你能用哪个资源 | 能用哪个助理、访问哪个数据域 |
| 数据范围 | 业务模块 | 你在这个资源里能看哪些行、哪些列 | 行规则、列脱敏 |

**IAM 统一"人是谁、能进哪个模块"；模块自己管"进去后能看什么资源、哪些行和列"。**

### 2. IAM 的职责边界

IAM 继续作为基础平台模块，负责：

- 用户、组织、角色、登录与令牌；
- 功能权限目录与角色授权；
- 模块入口级权限（能不能打开某个模块/管理页）；
- 为业务模块提供**只读**的角色目录与用户目录。

IAM **不再**：

- 存储或编辑 `DOMAIN` / `ASSISTANT` 的数据策略；
- 解析行规则、列规则、字段名、操作符；
- 跨服务读取 ask 的数据域/助理元数据。

### 3. 业务模块的职责

以 ask 为例：

- 资源定义（数据域、助理、表、字段）与资源级授权由 ask 自己维护；
- 行/列策略继续存 `ask_domain.perm_json` / `ask_assistant.perm_json`；
- 引擎只从本地策略读取并执行，**不再在问数热路径调用 IAM 取数据策略**；
- 策略缺失、解析失败、角色不匹配一律 **fail-closed**，沿用 ADR-0002 的判据；
- 策略变更审计（操作人、时间、版本、前后差异）由模块自己承担。

后续新增模块（报表、指标、工单等）照此办理：IAM 注册入口与功能权限，
模块自己实现资源授权与数据权限。

### 4. 引用契约

模块策略引用 IAM 的身份，但不复制身份数据：

- 角色：存 `iam_role.code`，不存显示名；code 一经使用不可重命名（ADR-0004）。
- 用户：存 `username`，不存用户表主键或显示名。
- IAM 停用/删除角色或用户后，模块侧必须能发现并提示；ask 已有的角色目录校验
  （`RoleHint`、启动校验）继续保留。
- 模块策略的 schema、版本与语义由模块自己定义；IAM 不参与校验。

### 5. 编辑入口

- 数据域/助理的权限在 **ask 管理台**编辑，与资源定义放在一起；
- IAM 管理台不再展示"数据策略"菜单，也不提供 DOMAIN/ASSISTANT 策略的写接口；
- 若未来需要"全公司数据权限总览"，由 IAM 或独立治理页通过模块的**只读**接口聚合，
  不把写入口搬回 IAM。

### 6. 迁移

1. 一次性把 `iam_policy` 中 `resource_type in ('DOMAIN','ASSISTANT')` 的文档
   迁移到对应资源的 `perm_json`；迁移前后做逐资源比对。
2. 保留 `policy.source=iam` 一个发布周期，用于回滚与双读校验；默认切到 `local`。
3. 校验通过后下线 ask 的 IAM 策略客户端与 IAM 的策略编辑页。
4. `iam_policy` 表可保留给未来其他通用策略，但不再是 ask 数据权限的事实来源；
   若无用途则一并删除。

## 考虑过的其他方案

- **全部留在 IAM（原方案）**：单点查看方便，但把领域 schema、资源元数据、
  生命周期都压给 IAM。模块越多，IAM 越难独立演进。
- **IAM 存策略、编辑器做成共享组件挂到 ask**：解决了入口问题，但 IAM 仍需理解
  两套文档结构，且 ask 调 IAM 写接口会引入第二套会话/CSRF/权限处理。
  在"模块自治"的目标下属于过度设计。
- **把资源定义也搬进 IAM**：会让 IAM 变成业务配置中心，与基础平台定位冲突。
- **模块自行维护用户/角色副本**：会造成身份多源，角色停用后权限静默失效，不可取。

## 后果

**正面**

- IAM 真正独立：不依赖 ask 的库、接口与领域模型，可服务任意新模块。
- 模块演进自由：新增规则类型、操作符、字段只改模块，不影响 IAM 发版。
- 问数路径更短：数据策略本地读取，IAM 抖动不影响已有策略执行。
- 编辑路径回归资源所在处，不需要在两个应用之间来回跳。

**负面 / 已知限制**

- **失去"一张表看全公司数据策略"。** 需要总览时只能做只读聚合。
- **模块各自实现审计与版本。** 需要约定最低要求，否则治理水平会不一致。
- **角色/用户引用可能漂移。** 依赖 IAM 角色码稳定 + 模块侧校验；IAM 不能静默
  删除仍被引用的角色（应在停用前提示影响面）。
- **迁移期存在两份数据。** 必须用 `policy.source` 开关与双读校验兜住，不能长期并存。

## 相关

- ADR-0002：数据权限的执行点在引擎。本 ADR 不改变它，只把策略存储从 IAM 移回模块。
- ADR-0004：角色码稳定、数据权限角色逐字符匹配。**继续有效**。
- ADR-0009：功能权限与数据权限正交。功能权限仍归 IAM；其中"数据权限存
  `iam_policy`"的表述由本 ADR 修订。
- `chatdata-agent-design/iam-platform/spec.md` §5.4：原"策略文档存 IAM"的设计由本 ADR 取代；
  身份、角色、功能权限部分继续有效。
