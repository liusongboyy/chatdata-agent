# 功能权限与内置超管：从「一个角色门」到「逐项权限」

> **部分被修订（2026-10-23）**：本文关于功能权限与数据权限正交、逐项权限码的结论
> **继续有效**；其中「数据权限存 `iam_policy`」已由
> [ADR-0010](0010-module-owned-data-policies.md) 改为由各业务模块存储与编辑。

## 背景

到 2026-10-22 为止，整个系统只有**一道粗粒度门槛**：`chat2bi` 角色。
`SecurityConfig` 用 `hasRole("chat2bi")` 守着 `/iam/admin/**`，
`AskSecurityConfig` 用 `hasAnyRole("chat2bi","admin")` 守着 `/api/engine/admin/**`，
两个前端的导航都是硬编码数组，全仓没有任何按权限的界面控制。

三个具体问题：

1. **没有中间档。** 想让某人只管「反馈审核」，只能把整个管理台都给他。
2. **界面不区分。** 没权限的人照样看到「删除」「重置密码」「通过/拒绝」，点下去才被拒——
   错误暴露得晚，也容易被当成"系统坏了"。
3. **超管的身份挂在一个语义不匹配的角色上。** 超管判定硬编码为角色码 `chat2bi`，
   而它的名字是「问数管理台」（ADR-0004 定的）。运维看角色列表，看到的是"问数管理台"，
   不会想到"这就是那个不能删的超级管理员"。

ADR-0004 的结论（`chat2bi` 只授予管理员、问数不依赖它）**继续有效**，
本 ADR 修改的是"权限怎么表达"与"谁是不可移除的超管"。

## 决定

### 1. 功能权限是一等公民，与数据权限正交

引入约 27 个权限码，三层（模块 → 页面 → 动作），定义在 IAM 的 `PermissionCatalog`。
它同时是：角色配置界面的数据源、保存时的校验基准、`@PreAuthorize` 里那些字符串的出处。

与 `iam_policy`（数据权限：能看哪些行、哪些列）是**两件事**，沿用 ADR-0004 的三分：

| | 存储 | 决定 |
|---|---|---|
| 功能权限 | `iam_role_permission(role_id, code)` | 能看到哪些页面、按钮、tab |
| 数据权限 | `iam_policy.document`（JSON） | 能看哪些行、哪些列 |

### 2. 粒度：页面 + 写 + 删，不是每个按钮一个码

创建与编辑几乎总是一起授予，拆开只会让配置界面从 3 行变成 9 行；**删除单独留下**（不可逆）。
问数页的四个图表形态收敛成一个 `ask.ui.charts`——它们是展示偏好，数据已整份返回，
拆成四个码是假的安全感。

### 3. 功能权限独立生效：持有任一页面权限即可进入管理台

不再要求 `chat2bi`。于是可以只给某人「反馈审核」。

### 4. 前后端逐项强制，且**判定同源**

- 前端：`can(code)` 隐藏导航、按钮、tab。**这不是安全边界**，只是把错误提前。
- 后端：每个接口一个码。IAM 用逐方法的 `@PreAuthorize("@perm.has(...)")` +
  **类级 `@PreAuthorize("false")` 默认拒绝**（漏挂一个方法是"用不了"，不是"对全员开放"）；
  ask 的 `AdminEngineController` 有 39 个端点，改用一张可测的规则表
  （`AdminApiPermissions`）+ 类级一个注解，并由**覆盖测试**断言每个映射都有规则。

**关键约束：界面展示与后端强制必须读同一份数据。** 最初的设计让
`loadUserByUsername`（会话 authorities）与 `loadPrincipal`（`/iam/me`）各算一份权限，
结果是**界面显示按钮、点下去全 403**，连内置超管也一样。现在两者都经
`EffectivePermissionResolver`（5 秒缓存），`@perm` 也走它。

### 5. 内置超管是独立的 `super_admin` 角色

在代码里展开为全部权限，不落 `iam_role_permission`，界面只读、不可停用。

`chat2bi` **降为普通可配置角色**，预置了它的描述所声称的那些码（管理面全部，不含 `ask.ui.*`）。
两者拆开的理由：让运维一眼认出哪一个才是那道保险。

| | `super_admin` | `chat2bi` |
|---|---|---|
| 权限 | 全部，代码展开 | 24 项预置，可编辑 |
| 可否编辑 | 不可 | 可以 |
| 可否停用 | 不可 | 可以 |
| 用途 | 兜底（break-glass） | 日常的管理台角色 |

### 6. 提权与锁死的防护

这些权限码里有几个**单项就等于超管能力**，光靠"有没有这个码"挡不住：

| 风险 | 防护 |
|---|---|
| `iam.users.write` 的请求体带 `roles`，可造一个超管账号 | 带 `roles` 的创建额外要求 `iam.users.roles` |
| 把超管授给别人 | 授出方必须自己已持有该角色 |
| `iam.roles.write` 停用内置超管角色 | 内置角色不可停用 |
| `iam.users.write` 停用最后一个超管用户 | 拒绝（否则只剩改库一条路） |

`PermissionCatalog` 把这些码标为 `sensitive`，配置界面单独提示。

### 7. 初始化：必须有带外的第一条路

全新部署时 `iam_role` 是空的，没有任何人能登录——而"登录进管理台去建角色"本身要求已经能登录。
这是鸡生蛋，只能靠带外手段解开：

- `sql/iam/08-bootstrap.sql`（幂等）：建 `super_admin` 角色，并**把现有 `chat2bi` 持有者补授
  `super_admin`**（不做这一步，升级那一刻现有管理员会失去全部权限）
- `bootstrap-admin` profile（`BootstrapAdminRunner`）：用**环境变量**提供的密码建第一个管理员账号。
  密码不写进 SQL——`02-seed-dev.sql` 那种硬编码哈希只适合本地开发。

## 考虑过的其他方案

- **给每个按钮一个权限码（约 37 个）**：配置界面变成一张长清单，而多数按钮的授予是成组的。
  收敛到 27 个之后仍覆盖了所有需要区分的动作（删除、重置密码、分配角色、测试连接、审核）。
- **把权限存成 `iam_role.permissions_json`**：与 `iam_policy` 的做法一致，但取"某用户的全部权限"
  要从多行 JSON 里合并，而关联表一条 join 就够，还能在 code 上建索引回答"谁有这项权限"。
- **用 `hasAuthority('PERM_...')` 直接判**：会读**会话里的 authorities**，而那是登录那一刻的快照；
  界面（`/iam/me`）却是实时的。两者不同源正是上面第 4 条那个坑。
- **给 `chat2bi` 保留超管身份**：就是本 ADR 要修的语义混淆。
- **保留一个"默认管理员密码"**：迟早被带到生产。

## 后果

**正面**

- 可以只给某人一个页面（如「反馈审核」），不再只能"全给或全不给"
- 界面不再显示点不了的按钮
- 绕过界面直接调接口同样被挡（每个接口都有码，且默认拒绝）
- 升级路径明确：`08-bootstrap.sql` 先跑，再上新版本，现有管理员不会掉权限

**负面 / 已知限制**

- **权限码在两处重复。** ask 不依赖 IAM 模块，`AdminApiPermissions` 里的字符串与
  `PermissionCatalog` 是两份。由 `PermissionCatalogTest.askCodesExist` 兜住漂移，
  但真正的修法是把目录挪进一个共享模块。
- **`ask.ui.*` 只是展示偏好，前端隐藏拦不住开发者工具。** 数据已经整份返回，
  这是刻意的取舍（不假装它是安全边界）。
- **权限变更的生效延迟 = 5 秒（IAM 自己）/ 30 秒（ask 的内省缓存）。**
- ~~**`EngineStartupCheck` / `RoleReferenceValidator` 校验的仍不是生效策略**——~~
  已在 2026-10-22 修掉：启动校验改按 `PolicyProvider` 取生效文档，角色清单来自
  IAM 角色目录（`GET /iam/policy/roles`）。IAM 不可用时跳过并记 WARNING。
  详见 `.scratch/iam-platform/spec.md` 的「P2 阶段三」。
- **关闭功能权限的开关（`chatdata.iam.functional-permissions.enabled`）会退回旧的
  `hasRole("chat2bi")` 行为**。它是回滚闸：没有它，IAM 一旦回滚（不再返回权限），
  ask 的管理面会整体 403。

## 相关

- ADR-0002：数据权限的执行点在引擎。本 ADR 不改变它——功能权限与数据权限正交。
- ADR-0004：`chat2bi` 只授予管理员、问数不依赖它。**继续有效**，本 ADR 在此基础上
  把 `chat2bi` 从"超管"降为普通角色。
- ADR-0008：不透明令牌与内省。权限随内省结果下发（`PERM_*` authority），
  **不放进 attributes**——那里是行规则 `dynamicVars` 的来源。
