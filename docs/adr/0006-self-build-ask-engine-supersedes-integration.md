# 自研问数与语义层，取代早期的「集成第三方引擎」决定

## 背景

早期决定是**集成**一个第三方 BI 产品承担语义层、NL2SQL、数据源适配与图表展现，本项目只自建治理层。其核心理由是工期：自研同路径估计 6–9 个月，其中 NL2SQL 准确率从 55% 提到 80% 依赖语料与评测集的持续迭代，**没有确定工期**。

**这个工期估算现在仍然成立，本次反转不否认它。** 反转的原因是 ADR-0001 的一个**未经验证的前提**被证伪了。

ADR-0001 隐含假设：集成之后，厂商侧的行为仍可在需要时修改。原文写的是"集成让我们把全部精力投在治理层"——这句话成立的前提是治理层之外的部分**不需要改**。

该前提在本次排查中被证伪：

| 事项 | 实测结果 |
|---|---|
| `-sources.jar` | 三个 starter 的 sources jar 均为**空壳**，只有 `README.md`，无一行 Java |
| 字节码 | **混淆**：包名与类名被压成单字母（如 `a/b.class`），方法名为 `a()` / `b()` |
| 页面模板 | **加密**：`META-INF/.templates/*` 为高熵密文（文件头为 ASN.1 DER 结构），明文检索 `needLogin` 零命中 |
| 前端 JS | 明文可读，且可被本项目 `static/` 覆盖（已注入 marker 实测验证） |

即：**后端是只读的黑盒，可改的只有前端 JS。**

这不是理论风险，本轮已经撞到两个无法修复的厂商缺陷：

1. **失效 token 导致页面永久卡死。** 登录页 `mounted()` 只判断 token 存不存在、不判断有效性。localStorage 里留有一个失效 token 时，页面跳过登录框、卡在"加载中…"，**没有任何回到登录页的路径**。已用真实浏览器复现（`needLogin:false`、页面文字"加载中…"、密码框数量 0）。模板加密，改不了。
2. **连接测试的三重缺陷。** 下拉列出 14 种数据库，jar 内**只有 MySQL 驱动**；失败提示是裸类名 `连接失败：org.postgresql.Driver`；且该路径没有 `DriverManager.setLoginTimeout`，打黑洞地址实测 **30 秒**才返回（积木报表自己的 `/jmreport/testConnection` 是有超时的）。

两者都属于"产品可用性问题"，在集成方案下**只能提 issue 或绕过**。

**第三个触发点：许可证。** 早期 ADR 已记录该产品声明 AGPL-3.0，而 POM 的 `<licenses>` 写的是"功能可以免费用"（非许可证标识符），需书面结论。自研彻底移除这项不确定性。

## 决定

**自研完整的问数系统，覆盖第三方产品当前已实现的全部能力**，技术栈 `agentscope-java 2.0.4` + `Spring Boot 4.1.0`。

范围：

1. 管理数据源
2. 语义数据表
3. 语义建模（语义域 / 注册表 / 查询主题 / 业务术语）
4. 助理管理
5. 问数链路（NL2SQL + 取数 + 图表 + 多轮追问）

具体决定：

- **前端新写 Vue 页面**，不复用厂商前端，也不走 `static/` 覆盖。理由是覆盖方案本质是 fork 一份加密模板所引用的 JS，升级时需逐文件比对；而自研的目标正是摆脱这种耦合。
- **本期不动现有第三方集成。** 新模块独立建库建表（前缀 `ask_`），与厂商的表前缀隔离。切换方式（并行共存渐进切换 / 直接替换）**另行决策，另出 ADR**。
- 详细规格见 `.scratch/self-built-chatbi/spec.md`。

## 考虑过的其他方案

- **维持集成（ADR-0001 原决定）**：工期最省，但承接上述三个问题，且已确认后端不可改。若厂商愿意出源码或商业授权，此方案可重新评估——但它现在是"等待外部条件"而不是"当下可执行"。
- **反编译混淆字节码打补丁**：技术上可行，但要维护一个混淆代码的 fork，每次升级重新 rebase。**不可行。**
- **只覆盖前端 JS，不改后端**：能修掉第 1 个缺陷（token 卡死），但第 2 个（驱动/超时）和权限层的默认放行缺口都在后端。**只能解决三分之一的问题。**
- **只自研管理面，问数继续用厂商**：看似折中，实际最差——两套系统要共用同一批厂商表（其 schema 无文档、且我们改不了它的代码），耦合度比现在更高。
- **向厂商谈商业授权或索取源码**：可同时解决许可证与可维护性。**建议并行推进**，若谈成可显著缩短工期；但它有商务周期，不应作为排期的前提。

## 后果

**正面**

- 后端完全可控，厂商侧的行为缺陷可在自己代码里修复。
- **能修掉厂商权限模型的默认放行缺口。** ADR-0002 实测记录了两处"默认放行"：域授权为空 = 对所有已认证用户开放；助手 `enabled` 缺失 = 对任何角色集放行。自研可改为默认拒绝 + 启动校验。
- 许可证不确定性移除。
- ADR-0002 的实测结论从"厂商行为描述"升级为**可继承的规格**——见下。

**负面**

- **承接 ADR-0001 的 6–9 个月估算，且 P4（准确率迭代）仍不可排期。** 这是本次反转的代价，必须在排期时如实反映，不能因为"自己写更可控"就低估。
- 前端从零写，厂商前端是加密模板抄不了（其 JS 是明文，可参考交互）。
- 并行运行期间存在两套语义模型漂移的风险。

**对既有 ADR 的影响**

| ADR | 影响 |
|---|---|
| （已删除）集成第三方引擎 | **Superseded by 本 ADR** |
| 0002 数据权限enforcement点 | **决定作废，结论保留**。"只实现 `JmReportTokenServiceI`、不自建 SQL 改写层"不再成立（没有厂商可复用）；但其**实测出来的权限语义**（两层闸门判据、默认放行缺口、角色名不可经 HTTP 头传递、被拒绝返回 200 的陷阱、等价字段脱敏遗漏）成为新实现的规格来源，已全文迁入 PRD §7 |
| 0003 事件级 SSE | 继续有效，新实现沿用 |
| 0004 角色模型 | 继续有效。管理台角色的结论直接继承 |
| 0005 临时密码认证 | 继续有效，与本次反转正交 |
