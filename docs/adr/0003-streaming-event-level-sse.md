# 流式采用事件级 SSE，不追求逐字流式

## 背景

问数一次要 5–15 秒：判定权限、生成 DSL、渲染 SQL、执行。如果这期间界面完全无反馈，
用户会以为卡死。可选的传输形态有三种：同步返回、逐字流式、事件级流式。

## 决定

**采用事件级 SSE，不追求逐字流式。**

1. 立即发出 `started` 事件——这是本决定的主要目的，消除「界面卡死」观感
2. 在**工作线程**上执行问数
3. 执行期间发**心跳事件**，避免长连接被中间层掐断
4. 完成后发 `result` 事件，载荷是完整结果（含 `dsl` / `sql` / `data` / `columns` / `chart`）

## 考虑过的其他方案

- **逐字流式**：问数的主产物是**结构化的**（DSL、SQL、结果集），逐字吐出这些没有意义——
  用户要的是"查到了什么"，不是"字正在被生成"。真正想逐字看的是最后那段文字结论，
  而它只占整条链路的一小部分时间。
- **不做流式，仅同步返回**：最简单，但会让 5–15 秒的过程完全无反馈，与已定的会话形态冲突。

## 后果

- **工作线程会跨线程，权限上下文必须显式传递。** `ThreadLocal` 中的身份/权限上下文
  不会自动传播到工作线程。必须在提交任务**前**捕获上下文、在任务内重设、在任务结束后清理。
  此处失败形态是**权限静默失效**（不过滤而非报错），与权限执行点的风险同源，需测试守护。
- **心跳间隔需与网关/反代超时对齐**，否则长耗时问数仍会被掐断。
- **事件级 SSE 的客户端契约比逐字简单**：前端只需处理
  `started` / `progress` / `heartbeat` / `result` / `error` 几类事件，无需增量拼接。
- **本决定不改变准确率或权限的任何行为**——纯属传输层形态。
