# 直连模式：只勾表，模型自己写 SQL；权限只到表级

## 背景

语义域要求先做语义建模（列别名、聚合、术语、主题、行/列权限），才可能问数。
建模成本高——而 PRD §10 已经把"语义建模工作量大"上调为**高风险**，并指出它同时是
准确率的主要杠杆。现实需求是：给一批业务用户快速开放某几张表，先让他们问起来。

所以需要**第二种模式**：只勾表，把表结构与采样值交给模型，让它自己写 SQL。

## 决定

给 `ask_domain` 加 `mode`：

- `MODELED`（默认）：现有链路，语义建模 → DSL → **我们渲染 SQL** → 注入行/列权限
- `RAW`：只勾表 → 模型自己写 SQL → 执行

### 关键约束：RAW 模式**只做表级授权**

模型写的 SQL 形状任意（CTE / UNION / 子查询 / 窗口函数），**没有安全的注入点**。
ADR-0002 已评估并否决"用 JSqlParser 解析后注入谓词"（正确性风险高于收益）。

因此该模式**不执行行级/列级规则**，且这一点在三处强制，不允许静默：

| 位置 | 做法 |
|---|---|
| 管理台保存 | `DomainInput.validated()` 拒绝带 `rowRules`/`colRules` 的 RAW 域 |
| 启动校验 | `EngineConfigValidator.validateRaw()` 报 `RAW_DOMAIN_WITH_RULES`（ERROR） |
| 问数页 | 明示「未启用行级/列级权限」 |

表级授权由 `SqlTools` 在**执行前**强制：用 JSqlParser 提取 SQL 引用的全部表名，
必须 ⊆ 白名单（`ask_domain_table` 里启用的表）。**不靠 prompt 请求模型自觉**——
模型可以被问题诱导去查 `sys_user`。

### 与 ADR-0002 的关系：不矛盾

ADR-0002 否决的是**改写 SQL**（要学会所有语法形态，改错了还是合法 SQL，风险高）。
这里只用 JSqlParser **读出 SQL 引用了哪些表**，一个字符都不改，读不懂就拒绝（fail-closed）。
失败形态是"拒绝执行"，不是"改错了但语法正确"。

## 考虑过的其他方案

- **新建 `ask_dataset` 实体**：语义更干净，但要重写一套 CRUD + 权限 + 路由 + 管理台页面。
  复用 `ask_domain` 的代价是"一个实体两种语义"，用不变量 + UI 标注来防混用。
- **把模型写的 SQL 解析后注入行规则**：ADR-0002 已否决。
- **只给管理员用**：不涉及权限降级，但业务上不满足需求。

## 后果

**正面**

- 无需建模即可问数，建模成本从"每人每表"降到"勾选"
- 所有复用：助理绑定、域级授权、SSE、审计、多轮会话、管理台

**负面 / 已知限制**

- **没有行/列权限**，敏感列只能靠"不把带敏感列的表勾进来"
- **没有 DSL 这个确定性检查点**，静默语义错误的风险高于建模模式；
  唯一的兜底是把模型写的 SQL 摊开给用户看
- 准确率不承诺：PRD §12 的实证显示裸 schema 上通用模型表现远低于语义层路径
- 未实现（P2）：多轮上下文（RAW 未挂 `AgentStateStore`）、图表推荐、
  模型中间推理的流式透出（届时 `FinalAnswerFilterMiddleware` 才有挂载点）

**建议**：生产环境给 RAW 域使用的数据源配一个**只读且仅授权这些表**的数据库账号，
作为应用层白名单之外的第二道防线。
