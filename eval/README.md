# 问数评测集

准确率不能靠"问一句看看"判断。这个目录存放**验收基线**：每条用例是一个中文问题
加一条已确认正确的 gold SQL，跑分时按**结果集**比对（EX）。

## 快速开始

```bash
# 1) 构建评测夹具库（一次性；可重复执行，会重建 chatdata_eval）
./eval/fixture/prepare.sh

# 2) 跑全部数据集
./eval/run.sh                    # 199 条（193 单查询 + 6 分析）
./eval/run.sh --limit 20         # 只跑前 20 条，调 prompt 时用
```

`run.sh` 会先安装 ask-engine，再以 `eval` profile 启动应用。模型密钥与数据源密钥
从环境变量读取（本地可用 `~/.chatdata-agent.env`）。

## 为什么要夹具库，而不是直接跑业务库

初版评测跑在业务库（`jimureport.aiticket`）上，有 3 张工单。这带来两个问题：

1. **HARD 用例没有信号。** 分组只有 1–2 行，任何查询都"碰巧对"或者"碰巧空"。
2. **基线不可复现。** 业务数据一改，昨天的分数与今天不可比，而"这次比上次准了"
   就失去依据。

因此有了 `eval/fixture/`：独立 schema `chatdata_eval`，数据由固定随机种子生成，
任何机器上跑出来完全一致。

| 表 | 行数 |
|---|---|
| `ticket` | 2,000 |
| `ticket_flow` | 6,486 |
| `ticket_comment` | 2,575 |
| `sla_violation` | 669 |
| `notification` | 500 |
| `knowledge_article` | 300 |
| `knowledge_attachment` | 60 |
| `ins_policy` / `ins_customer` / `ins_claim` | 300 / 80 / 128 |

保险那三张是真实数据的快照（`02-insurance-data.sql`），工单那批由
`generate-ticket-data.py` 用种子 `20260101` 生成。**改生成脚本 = 改基线**，
改完必须重跑全部数据集并更新本文的分数。

### 三个评测域

| 域 id | 名称 | 模式 | 表数 |
|---|---|---|---|
| 2001 | 保险分析域（评测夹具） | 建模 | 3 |
| 2002 | 工单分析域（评测夹具） | 建模 | 4 |
| 2003 | 工单直连域（评测夹具） | 直连 | 12 |

建模域还配了三个**派生指标**，用来覆盖「指标之间的运算」这类问法：
`赔付率`（赔付金额 ÷ 申请理赔金额）、`赔付差额`（两者相减）与
`平均解决时长`（生效日期 → 解决时间，按小时）。派生指标定义在语义层，
模型在 DSL 里只引用名字、不写算式——对应 `insurance-061/062`、`ticket-m-061`。

排序 / 占比 / 同环比同样有专门用例，覆盖 DSL 的三个新字段：
`insurance-063`（Top-N）、`insurance-064` / `ticket-m-063`（占比）、
`insurance-065`（同比）、`insurance-066`（自定义对比期）、`ticket-m-062`（Top-N）。

**带条件的指标**也有专门用例：`ticket-m-064`（已解决占比 = 条件指标 ÷ 总工单数）、
`ticket-m-065`（直接用条件指标）、`ticket-m-066`（AND 两条件）、
`ticket-m-067`（OR 两条件）。夹具里配了「已解决工单数」「高优已解决工单数」
「未完成工单数」——后两个是 AND / OR 多条件形态。

建模域的软删过滤写在 **SQL 虚拟表**定义里（`SELECT * FROM ticket WHERE deleted = 0`）。
这不是绕开问题：`deleted` 是实现细节，不该出现在列定义里；"必须过滤软删"
是这张表的业务口径，本来就属于建模。

## 当前基线（2026-10-26 分析编排上线）

**同一份代码连跑多次的实测波动约 ±3 个百分点**（模型输出随机性；temperature 已为 0
但提供方仍非确定性）。所以单次跑分不足以判断改动好坏，至少跑 2–3 次看区间，
CI 门禁阈值也要设在区间下沿再留余量。

最近一次：

| 数据集 | 主指标 | 严格 EX | 包含式 EX |
|---|---|---|---|
| 保险分析域（建模） | 严格 | 50/66 = 75.8% | 75.8% |
| 保险分析域 · **分析编排** | 见下方说明 | 6/6 = 100% | 6/6 = 100% |
| 工单分析域（建模） | 严格 | 46/67 = 68.7% | 47/67 = 70.1% |
| 工单直连域（直连） | **包含式** | 28/60 = 46.7% | **41/60 = 68.3%** |
| **合计** | 按各集主指标 | 130/199 = 65.3% | **143/199 = 71.9%** |

分档：SIMPLE 53/65、MEDIUM 42/72、HARD 26/56。

保险域两种口径**完全相同**——语义层把字段收敛住了，模型没有"多带列"的余地；
工单建模域完全一致。直连域差 13 条，全在多余列上；
这一差异本身就是"语义层有用"的直接证据。

### 已修复的能力缺口

| 缺口 | 修复 | 效果 |
|---|---|---|
| **时间粒度被丢弃** | `DslParser` 曾完全不解析 `granularity`，模型填了 `month`/`year` 也被丢掉，渲染器按天分组。同时业务规则 prompt 里没提这个字段 | 保险域 56.7% → 63.3%，HARD 档 15 → 19 |

`granularity` 那条值得记下来：链路上每一环单独看都没问题——schema 定义了字段、
渲染器支持截断、`AskDsl` 有默认值——只有串起来才发现解析器根本没带它。
`DslParserTest` 与 `PromptAssemblerTest` 现在各自钉住一半。

## 指标口径

| 指标 | 定义 | 为什么要单列 |
|---|---|---|
| 严格 EX 通过率 | 列数、行数、值全部一致 /（总数 - gold 错误） | 与 BIRD / Spider 的 EX 口径一致，是可对外比较的主指标 |
| 包含式 EX 通过率 | gold 的列都能在实际结果里匹配上，**多返回的列不算错** / 同分母 | 把"答案对但话多"与"答案错"分开 |
| 空结果率 | 执行成功但 0 行，而 gold 有数据 | 真实场景最大杀手，常被总分掩盖 |
| 静默语义错误率 | 执行成功、无异常，但结果不对（含空结果） | 不报错、数字看着正常，是数据系统最危险的失败形态 |
| 分档通过率 | SIMPLE / MEDIUM / HARD | 总分会被简单题淹没，短板通常在 HARD |

### 直连模式该不该用严格 EX

**不该。** 直连域的失败里绝大多数是"多余列"——模型查对了数据，只是顺手多带了
id、名称之类的上下文列。那是直连模式的设计使然（没有语义层收敛字段范围），
把它算成错会让这个数字失去指导意义。

**已落地**：评测集可以声明 `primaryMetric`，由它决定该集的验收口径。

```json
{ "domainId": "2003", "primaryMetric": "contains", ... }
```

- 取值：`strict`（默认）/ `contains`，也接受中文「严格」「包含式」
- 两种口径**始终都会报告**，`primaryMetric` 只决定哪一个是验收依据
- 总览里的「按各集主指标」与 CI 门禁用的就是这一行；严格 / 包含式两个总数仍并列显示
- **由数据集自己声明，不按 mode 自动推断**：mode 是运行时结果（同一批用例可能 MIXED），
  而"用什么口径验收"是评审决策，藏进推断逻辑里会让改口径变成看不见的副作用

## 新增一个数据集

1. 在 `eval/` 下新建 `<数据集名>.json`（文件名任意，按名称排序执行）
2. 填 `domainId`（`ask_domain.id`）、跑分身份 `userId` / `roles`、用例列表
3. 跑 `./eval/run.sh`，确认没有 `GOLD_ERROR`

**不需要改代码或配置**——目录里所有 `*.json` 都会被加载。

`eval/legacy/` 放着初版跑在业务库上的两个数据集（域 1 / 1372），
**不参与默认运行**（`loadAll` 只看目录第一层）。需要对照历史分数时用
`./eval/run.sh --path ../eval/legacy/ticket-domain.json`。

### 文件格式

```json
{
  "name": "智能工单域基线",
  "domainId": "2002",
  "userId": "eval",
  "roles": ["super_admin"],
  "assistantId": null,
  "primaryMetric": "strict",
  "cases": [
    {
      "id": "ticket-m-001",
      "difficulty": "SIMPLE",
      "question": "工单总数是多少？",
      "goldSql": "SELECT COUNT(*) AS cnt FROM ticket WHERE deleted = 0",
      "ordered": false,
      "columnOrder": "ANY",
      "tags": ["count"],
      "note": "口径说明，不参与判定"
    }
  ]
}
```

- `difficulty`：`SIMPLE`（单表聚合）/ `MEDIUM`（join、时间窗、分组）/ `HARD`（业务口径）
- `ordered`：行序是否参与比对。**只有带 LIMIT 的"前 N 名"才需要 true**
- `columnOrder`：`ANY`（默认）/ `STRICT`
- `primaryMetric`：`strict`（默认）/ `contains`。省略即严格 EX
- `roles` 必须能通过目标域的授权，否则每条都会是 `DENIED`
- **跑分身份必须对目标域有完整可见性**（无行级规则、无脱敏列）

### gold SQL 编写规范

- **只读**，一条 `SELECT` / `WITH`
- **结果确定**：不要依赖 `NOW()`、`CURDATE()`、`RAND()`；时间范围写死具体日期
- **列要少而准**：问题问什么就返回什么，不要 `SELECT *`
- 有 `LIMIT` 时必须有唯一排序键，否则并列值的顺序不稳定，会制造假失败
- 先手工执行一遍确认有结果；如果预期就是空结果，在 `note` 里写清楚

`build.py`（见下）会自动校验这几条。

### 生成与校验用例

用例定义在 `eval/build-cases.py`（Python 列表：id / 难度 / 问题 / gold SQL /
ordered / tags），它做三件事：

1. 每条 gold SQL 都在 `chatdata_eval` 上**实际执行**一遍——执行失败或结果为空
   直接剔除，不让有问题的用例混进基线
2. 校验不含 `CURDATE()`/`NOW()`/`RAND()`，且建模域引用的表都已注册
3. 产出 `eval/*-fixture.json`

```bash
python3 eval/build-cases.py
```

脚本是幂等的：同样的输入产出逐字节相同的 JSON。

### 分析编排怎么评

`analysis-fixture.json` 的判定**不是**结果集比对——分析模式返回的是
「步骤数据 + 确定性事实 + 结论」，不是一张表。只看第一张表对不对，
等于只检查了"第一步查得准不准"，而编排真正的风险在另外两处：

| 判什么 | 为什么 |
|---|---|
| 步骤失败数 ≤ 上限（默认 0） | 缺一步的结论比单查询更误导 |
| 期望的事实都出现（`CONTRIBUTION:华东`） | 该发现的变化没发现，SQL 照样全对 |
| 结论存在 | 空白结论让用户只看到一堆表 |
| 结论里没有禁用数字 | 抓"模型编了一个数"——运行时白名单之外的第二道闸 |

用例写在 JSON 里用 `analyze: true` + `analysis: {...}` 标记，
`EvalRunner` 遇到就调 `analyzeStreaming` 并交给 `AnalysisCaseChecker`。

**这套评测第一次跑就抓到两个真问题**（都是产品缺陷，不是用例写错）：

1. 规划器会给"构成"类问题顺手加 `compare` 却没给对比期 → 渲染期失败 →
   整条计划作废退化成单查询。修法：`compare` 是模型自加的增强而非用户约束，
   不成形时**丢掉它继续**，而不是废掉整条计划（`AnalysisPlanParser.sanitize`）。
2. 「保费总额是多少」这类标量问题原本**一条事实都算不出来**，结论区空白。
   修法：新增 `SCALAR` 事实类型。

### 建模侧补的两类能力（2026-10-26）

这两条以前是"引擎表达不了"，现在是**建模时多写一行**就行：

| 能力 | 怎么配 | 效果 |
|---|---|---|
| **时间口径显式声明** | 术语的 `applyKind=time`，术语名就是要用的日期列别名 | 域里同时有「生效日期」「报案日期」时，不再一律猜生效日期；`insurance-057` 从 ERROR 转 PASS |
| **同一字段兼作指标与维度** | 同一 `col` 登记两行：一行带聚合（指标），一行不带（维度） | 「50 岁以上的客户」`WHERE age > 50` 可解析；`insurance-048` 转 PASS |

解析规则：同名多个候选时，**恰好一个符合期望角色就用它**；一个都不符合、或多个都符合（真冲突）仍然拒绝。
权限字段定位（`resolveAny`）**保持严格**——谓词注错表比查询失败危险得多。

保险域 68.2% → 75.8%（两次跑分 75.8% / 74.2%，在 ±3pp 内）。

### 分析编排已具备（2026-10-26）

| 能力 | 说明 |
|---|---|
| 每步独立图表 | 趋势→折线、构成→柱、单值→数字卡；失败或无推荐时退回表格 |
| 多轮追问 | 上一轮的分析摘要（意图/步骤/事实/结论）进下一轮规划 prompt，追问「那华南呢」不再是缺主语的新问题 |
| **不做自动路由** | 保持界面上的「深入分析」显式开关。理由：路由判错没有兜底，且现有评测集没有模糊地带用例，等于上一个无测试覆盖的判断逻辑 |

### 列描述画像：实测收益接近零（2026-10-26）

给已注册的列做取值画像、生成描述并注入 prompt，是业界公认的高性价比手段
（BIRD 企业级研究：无列注释 66.5% → 有注释 73.8%）。本仓库实现了它，但**实测没有提升**：

| 条件 | 保险域（多次） |
|---|---|
| 有描述 | 75.8% / 74.2% / 74.2% / 75.8% |
| 无描述（对照） | 74.2% |

差异完全落在 ±3pp 的模型波动内。原因不是功能有问题，而是**对照组不同**：

1. **本项目的基线并不"裸"。** `ask_term` 里已经配了
   「保单状态 → 取值：生效、已过期、退保（中文，与库内一致）」这类术语。
   BIRD 的对照组是完全没有列注释的裸 schema。
2. **画像生成的是模板句**（「保单状态（varchar），取值 X、Y、Z，共 3 种」），
   信息量**低于**已有术语——后者还说明了"中文，与库内一致"，而那正是模型最容易错的地方。
3. **剩余失败不是列理解问题**：16 条失败里 4 条是多返回列、1 条是聚合字段当维度，
   其余是口径算错。知道 status 有 3 个取值解决不了这些。

**结论**：功能保留（对**新建的、尚未配术语的域**仍有价值——那些域是真"裸"的），
但**不要指望它在已配术语的域上提升数字**。若要在这条线上继续投入，方向应是
"用模型把画像写成业务描述"且"只对没有术语覆盖的字段生成"，而不是模板拼装。

### 建模覆盖度检查

上面那次测量的真正启示不是"要更多描述"，而是**建模覆盖度是单查询基线最大的杠杆**。
完整经验（为什么静默、新建域检查清单、反面清单）见
[docs/modeling-coverage.md](../docs/modeling-coverage.md)；这里只留结论与本目录的实测数据。
`ModelingCoverageCheck` 把这件事做成可执行的检查，管理员建完域当场能跑：

```
GET /api/engine/admin/domains/{id}/modeling-check
```

四类提示（全部 WARNING，不阻断启动）：

| 检查 | 提示什么 |
|---|---|
| 聚合覆盖 | 有数值列却没有任何 AVG；有分类列却没有任何 COUNT_DISTINCT |
| 指标/维度双登记 | 像"离散量"的数值列（年限/年龄/优先级）只有指标没有维度 |
| 时间口径 | 多个日期列，但没有任何 apply_kind=time 的术语 |
| 自相矛盾 | 统计条件引用了它自己（循环定义） |

**刻意不接进 `EngineConfigValidator`**：那个回答"能不能用"，这个回答"配得够不够好"。
混在一起会让"这个域缺 AVG"看起来像启动问题，而它并不该拦住启动。

提示的收窄也经过一轮：最初对**所有**数值指标报"缺维度"，结果每个金额列都被点名，
噪音大到没人会看。现在只对列名像离散量的（year/age/level/priority/次数/年限…）提示。

### 聚合覆盖是单查询基线最大的杠杆（2026-10-26 实测）

保险域从 **74.2% → 83.3%**（两次 83.3% / 81.8%），只改了一件事：
**把三种最常用的聚合形态登记进夹具**。

| 补的登记 | 修掉的失败 |
|---|---|
| `province` → `COUNT_DISTINCT`「省份数」 | 「一共涉及多少个省份」（模型原来只能列出每个省） |
| `premium` → `AVG`「平均保费」 | 「平均每张保单的保费」（原来出 SUM + COUNT） |
| `term_years` → 另加一条不聚合的「保障年限」 | 「保障年限为 10 年的保单」（原来只有 AVG 那条） |

引擎本来就支持 `COUNT_DISTINCT` / `AVG`，**只是建模里没人登记**。模型的反应很诚实：
没有对应指标，它就拿 `SUM`/`COUNT` 硬凑，凑出来的形态与问题不符。

**这比改 prompt 有效得多**，也说明了为什么「建模覆盖度」比「模型能力」更值得投。
新建域时应检查这几类形态是否齐备：去重计数、平均数、以及"同一字段的指标/维度双登记"。

### 评测集清理（2026-10-27）

做多值字段之前先清了一遍评测集，因为**基线不可信时，后面所有判断都失去依据**。
三类问题，处理方式不同：

| 类型 | 例子 | 处理 |
|---|---|---|
| **gold 写错** | `insurance-031`「保额最高的那类险种」的 gold 漏了 `GROUP BY`，实际是取单行最大值；`ticket-m-014/021/044/056` 的分母写成"有记录的行数"而非"全部工单" | 改 gold |
| **问题措辞有歧义** | 「2025 年**生效**的保单」里的"生效"指生效日期，但库里有个 `status='生效'`，模型两边都能理解 | 改问法（"2025 年**投保**的"），歧义本身留作已知陷阱 |
| **夹具漏登记** | 列在库里但没注册（`ai_category_id`、理赔表的 `product_type`、客户的 `region`）；或缺 MAX/MIN/AVG 聚合 | 补登记 |

结果：保险域 80.3% → **87.9%**，工单建模域 73.1%。

**这一步不提升产品能力**，但让基线变得可解释——之前 80% 里混着"产品对但 gold 窄"的用例，
看数字会误判方向。清理后剩下的失败基本都是真实缺口。

### 同名不同义：维度的归属歧义

清理时发现一个真实的建模陷阱：**同一个物理列在多张表上含义不同**。

`ins_claim.province` 是**出险地**，`ins_policy.province` 是**出单地**——
128 条理赔里 121 条不一致。问「各区域的理赔赔付金额」，两个口径会得到完全不同的答案。

当前的做法是**把别名起得不一样**（「出险省份」/「出单省份」），这是对的。
但依赖管理员每次都想到，所以补了一条检查：

> 同一物理列在 ≥2 张表上注册、跨表的业务名相同或不足以区分、且没有 description →
> 提示「模型只能靠猜」

判据的细节：
- 同一张表内的同名双登记（指标/维度）**不算**冲突，它是刻意的建模手法
- 别名互不相同 → 名字本身已能区分，不提示
- 都有 description → 已说清，不提示

对应地，`insurance-017` 这条用例本身是**歧义题**（问题没说按哪个口径），
不是产品缺陷，改问法为「按出险省份统计理赔赔付金额合计」。

### 表的默认过滤条件

清理过程中确认了一个真实缺口：模型会给问题**自行补过滤条件**。
问「2025 年保费合计」，它补上 `AND status = '生效'`——SQL 合法、数字合理，
只是少了三分之一，用户看不出差别。

新增 `ask_domain_table.base_filter`（`sql/20-ask-table-base-filter.sql`）：
管理员在建模里声明「什么算有效数据」，渲染器固定拼进 WHERE，模型不必猜。

- 片段**不经模型产出**，因此没有注入面；渲染器仍拒绝含 `?` 的片段（会打乱参数顺序）
- 只拼**参与本次查询的表**的条件——没 JOIN 进来的表拼它的条件会 `Unknown column`
- 物理表的裸列名会被补上表别名并按方言加引号，避免多表歧义与保留字冲突

## 已知的能力边界（基线暴露出来的）

这些不是"模型不够聪明"，是**产品当前表达不了**。改夹具绕过去是自欺，
应当作为功能缺口排期：

| 缺口 | 表现 | 影响的用例 |
|---|---|---|
| **「这个字段该用哪种说法」仍需模型选对** | 同一字段登记了「评论数」（指标）与「评论条数」（维度）后，模型在筛选时仍可能挑指标那条，于是被拒。解析层已能按角色择优，但**按名字挑**这一步靠模型 | ticket-m-043 |
| **直连域没有语义层收敛** | 模型自己写 SQL，多带列是常态；用严格 EX 衡量它会让数字失去指导意义（故该集用包含式作主指标） | 直连域整体 |

## CI 门禁

```bash
CHATDATA_EVAL_MIN_PASS_RATE=0.5 ./eval/run.sh
```

低于阈值时进程返回非 0。门禁看的是**「按各集主指标」那一行**。

阈值别卡在基线附近：模型随机性带来 ±3 个百分点的波动（见上文表格），
设成 0.55 会红在一个正常的抖动上，然后就没人再看这条门禁了。

**每次改 prompt / 换模型 / 改渲染器都跑一遍**，否则"感觉变准了"没有任何证据。

## 已知局限

- **静默语义错误率是近似值**：定义为"执行成功但结果不一致"。它抓得住"漏了条件导致数字不同"，
  但抓不住"错得恰好与原结果相同"的极小概率情况
- **EX 不等于业务正确**：gold SQL 本身写错时，评测会把正确答案判错。所以 gold 必须人工审核
- **要花模型调用**：199 条约 15–20 分钟、一千多次模型调用；分析集每条约 2–12 秒（含拆解与写结论两次模型调用）
- **评测会写审计**：与真实问数一样落 `ask_audit_log`，审计身份是 `eval:<数据集名>`，
  可用 `WHERE username LIKE 'eval:%'` 过滤掉
