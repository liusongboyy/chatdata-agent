# 问数评测集

准确率不能靠"问一句看看"判断。这个目录存放**验收基线**：每条用例是一个中文问题
加一条已确认正确的 gold SQL，跑分时按**结果集**比对（EX）。

## 快速开始

```bash
# 1) 构建评测夹具库（一次性；可重复执行，会重建 chatdata_eval）
./eval/fixture/prepare.sh

# 2) 跑全部数据集
./eval/run.sh                    # 183 条
./eval/run.sh --limit 20         # 只跑前 20 条，调 prompt 时用
```

`run.sh` 会先安装 ask-engine，再以 `eval` profile 启动应用。模型密钥与数据源密钥
从环境变量读取（本地可用 `~/.chatdata-agent.env`）。

## 为什么要夹具库，而不是直接跑业务库

初版评测跑在业务库（`jimureport.aiticket`）上，有 3 张工单。这带来两个问题：

1. **HARD 用例没有信号。** 分组只有 1–2 行，任何查询都"碰巧对"或者"碰巧空"。
2. **基线不可复现。** 业务数据一改，昨天的分数与今天不可比，而"这次比上次准了"
   就失去依据。

因此有了 `eval/fixture/`：独立 schema `chatdata_eval`，数据由固定随机种子生成，
任何机器上跑出来完全一致。

| 表 | 行数 |
|---|---|
| `ticket` | 2,000 |
| `ticket_flow` | 6,486 |
| `ticket_comment` | 2,575 |
| `sla_violation` | 669 |
| `notification` | 500 |
| `knowledge_article` | 300 |
| `knowledge_attachment` | 60 |
| `ins_policy` / `ins_customer` / `ins_claim` | 300 / 80 / 128 |

保险那三张是真实数据的快照（`02-insurance-data.sql`），工单那批由
`generate-ticket-data.py` 用种子 `20260101` 生成。**改生成脚本 = 改基线**，
改完必须重跑全部数据集并更新本文的分数。

### 三个评测域

| 域 id | 名称 | 模式 | 表数 |
|---|---|---|---|
| 2001 | 保险分析域（评测夹具） | 建模 | 3 |
| 2002 | 工单分析域（评测夹具） | 建模 | 4 |
| 2003 | 工单直连域（评测夹具） | 直连 | 12 |

建模域还配了三个**派生指标**，用来覆盖「指标之间的运算」这类问法：
`赔付率`（赔付金额 ÷ 申请理赔金额）、`赔付差额`（两者相减）与
`平均解决时长`（生效日期 → 解决时间，按小时）。派生指标定义在语义层，
模型在 DSL 里只引用名字、不写算式——对应 `insurance-061/062`、`ticket-m-061`。

建模域的软删过滤写在 **SQL 虚拟表**定义里（`SELECT * FROM ticket WHERE deleted = 0`）。
这不是绕开问题：`deleted` 是实现细节，不该出现在列定义里；"必须过滤软删"
是这张表的业务口径，本来就属于建模。

## 当前基线（2026-10-25）

**同一份代码连跑多次的实测波动约 ±3 个百分点**（模型输出随机性；temperature 已为 0
但提供方仍非确定性）。所以单次跑分不足以判断改动好坏，至少跑 2–3 次看区间，
CI 门禁阈值也要设在区间下沿再留余量。

最近一次：

| 数据集 | 主指标 | 严格 EX | 包含式 EX |
|---|---|---|---|
| 保险分析域（建模） | 严格 | 39/62 = 62.9% | 62.9% |
| 工单分析域（建模） | 严格 | 40/61 = 65.6% | 65.6% |
| 工单直连域（直连） | **包含式** | 29/60 = 48.3% | **39/60 = 65.0%** |
| **合计** | 按各集主指标 | 108/183 = 59.0% | **118/183 = 64.5%** |

分档：SIMPLE 50/64、MEDIUM 36/65、HARD 22/54。

建模域两种口径**完全相同**——语义层把字段收敛住了，模型没有"多带列"的余地。
直连域差 10 条，全在多余列上；这一差异本身就是"语义层有用"的直接证据。

### 已修复的能力缺口

| 缺口 | 修复 | 效果 |
|---|---|---|
| **时间粒度被丢弃** | `DslParser` 曾完全不解析 `granularity`，模型填了 `month`/`year` 也被丢掉，渲染器按天分组。同时业务规则 prompt 里没提这个字段 | 保险域 56.7% → 63.3%，HARD 档 15 → 19 |

`granularity` 那条值得记下来：链路上每一环单独看都没问题——schema 定义了字段、
渲染器支持截断、`AskDsl` 有默认值——只有串起来才发现解析器根本没带它。
`DslParserTest` 与 `PromptAssemblerTest` 现在各自钉住一半。

## 指标口径

| 指标 | 定义 | 为什么要单列 |
|---|---|---|
| 严格 EX 通过率 | 列数、行数、值全部一致 /（总数 - gold 错误） | 与 BIRD / Spider 的 EX 口径一致，是可对外比较的主指标 |
| 包含式 EX 通过率 | gold 的列都能在实际结果里匹配上，**多返回的列不算错** / 同分母 | 把"答案对但话多"与"答案错"分开 |
| 空结果率 | 执行成功但 0 行，而 gold 有数据 | 真实场景最大杀手，常被总分掩盖 |
| 静默语义错误率 | 执行成功、无异常，但结果不对（含空结果） | 不报错、数字看着正常，是数据系统最危险的失败形态 |
| 分档通过率 | SIMPLE / MEDIUM / HARD | 总分会被简单题淹没，短板通常在 HARD |

### 直连模式该不该用严格 EX

**不该。** 直连域的失败里绝大多数是"多余列"——模型查对了数据，只是顺手多带了
id、名称之类的上下文列。那是直连模式的设计使然（没有语义层收敛字段范围），
把它算成错会让这个数字失去指导意义。

**已落地**：评测集可以声明 `primaryMetric`，由它决定该集的验收口径。

```json
{ "domainId": "2003", "primaryMetric": "contains", ... }
```

- 取值：`strict`（默认）/ `contains`，也接受中文「严格」「包含式」
- 两种口径**始终都会报告**，`primaryMetric` 只决定哪一个是验收依据
- 总览里的「按各集主指标」与 CI 门禁用的就是这一行；严格 / 包含式两个总数仍并列显示
- **由数据集自己声明，不按 mode 自动推断**：mode 是运行时结果（同一批用例可能 MIXED），
  而"用什么口径验收"是评审决策，藏进推断逻辑里会让改口径变成看不见的副作用

## 新增一个数据集

1. 在 `eval/` 下新建 `<数据集名>.json`（文件名任意，按名称排序执行）
2. 填 `domainId`（`ask_domain.id`）、跑分身份 `userId` / `roles`、用例列表
3. 跑 `./eval/run.sh`，确认没有 `GOLD_ERROR`

**不需要改代码或配置**——目录里所有 `*.json` 都会被加载。

`eval/legacy/` 放着初版跑在业务库上的两个数据集（域 1 / 1372），
**不参与默认运行**（`loadAll` 只看目录第一层）。需要对照历史分数时用
`./eval/run.sh --path ../eval/legacy/ticket-domain.json`。

### 文件格式

```json
{
  "name": "智能工单域基线",
  "domainId": "2002",
  "userId": "eval",
  "roles": ["super_admin"],
  "assistantId": null,
  "primaryMetric": "strict",
  "cases": [
    {
      "id": "ticket-m-001",
      "difficulty": "SIMPLE",
      "question": "工单总数是多少？",
      "goldSql": "SELECT COUNT(*) AS cnt FROM ticket WHERE deleted = 0",
      "ordered": false,
      "columnOrder": "ANY",
      "tags": ["count"],
      "note": "口径说明，不参与判定"
    }
  ]
}
```

- `difficulty`：`SIMPLE`（单表聚合）/ `MEDIUM`（join、时间窗、分组）/ `HARD`（业务口径）
- `ordered`：行序是否参与比对。**只有带 LIMIT 的"前 N 名"才需要 true**
- `columnOrder`：`ANY`（默认）/ `STRICT`
- `primaryMetric`：`strict`（默认）/ `contains`。省略即严格 EX
- `roles` 必须能通过目标域的授权，否则每条都会是 `DENIED`
- **跑分身份必须对目标域有完整可见性**（无行级规则、无脱敏列）

### gold SQL 编写规范

- **只读**，一条 `SELECT` / `WITH`
- **结果确定**：不要依赖 `NOW()`、`CURDATE()`、`RAND()`；时间范围写死具体日期
- **列要少而准**：问题问什么就返回什么，不要 `SELECT *`
- 有 `LIMIT` 时必须有唯一排序键，否则并列值的顺序不稳定，会制造假失败
- 先手工执行一遍确认有结果；如果预期就是空结果，在 `note` 里写清楚

`build.py`（见下）会自动校验这几条。

### 生成与校验用例

用例定义在 `eval/build-cases.py`（Python 列表：id / 难度 / 问题 / gold SQL /
ordered / tags），它做三件事：

1. 每条 gold SQL 都在 `chatdata_eval` 上**实际执行**一遍——执行失败或结果为空
   直接剔除，不让有问题的用例混进基线
2. 校验不含 `CURDATE()`/`NOW()`/`RAND()`，且建模域引用的表都已注册
3. 产出 `eval/*-fixture.json`

```bash
python3 eval/build-cases.py
```

脚本是幂等的：同样的输入产出逐字节相同的 JSON。

## 已知的能力边界（基线暴露出来的）

这些不是"模型不够聪明"，是**产品当前表达不了**。改夹具绕过去是自欺，
应当作为功能缺口排期：

| 缺口 | 表现 | 影响的用例 |
|---|---|---|
| **`Term.applyKind=TIME` 未接入渲染** | 想按「注册日期」「报案日期」问时间，引擎只认 `生效日期/统计日期/业务日期/日期/时间` 这几个别名；否则报"找不到可用的日期列" | insurance-057 等 |
| **同一字段不能既是指标又是维度** | 「50 岁以上的客户」把「平均年龄」当维度用，被拒绝；正确做法是再登记一条不聚合的列 | insurance-048、ticket-m-043、ticket-m-053 |
| **DSL 无排序 / 无 Top-N** | 「评论数最多的前 5 张工单」渲染不出 `ORDER BY ... LIMIT 5` | ticket-m-019 |
| **DSL 无列间比较** | 「关闭时间晚于 SLA 截止时间」被当成日期字面量校验 | ticket-m-030、ticket-m-057 |
| **DSL 无跨列运算** | 「解决时长」= 两个时间列相减，DSL 没有表达 | ticket-m-025/026/029/051/060 |
| **DSL 无比值 / 占比表达式** | 「已解决占比」「内部备注占比」只能用 CASE WHEN，DSL 无表达 | ticket-m-024/027/052/053/055/057 |

## 报告

- 终端：总览 + 每个数据集一段 + 未通过明细
- JSON：`chatdata-agent-ask/target/eval-report.json`
  - 顶层是 `EvalSuiteReport`（多数据集汇总）
  - `reports[]` 每个数据集一份 `EvalReport`
  - 每条用例带 `goldSql`、`generatedSql`、行数、耗时、失败原因

## CI 门禁

```bash
CHATDATA_EVAL_MIN_PASS_RATE=0.5 ./eval/run.sh
```

低于阈值时进程返回非 0。门禁看的是**「按各集主指标」那一行**。

阈值别卡在基线附近：模型随机性带来 ±3 个百分点的波动（见上文表格），
设成 0.55 会红在一个正常的抖动上，然后就没人再看这条门禁了。

**每次改 prompt / 换模型 / 改渲染器都跑一遍**，否则"感觉变准了"没有任何证据。

## 已知局限

- **静默语义错误率是近似值**：定义为"执行成功但结果不一致"。它抓得住"漏了条件导致数字不同"，
  但抓不住"错得恰好与原结果相同"的极小概率情况
- **EX 不等于业务正确**：gold SQL 本身写错时，评测会把正确答案判错。所以 gold 必须人工审核
- **要花模型调用**：183 条约 15–20 分钟、一千多次模型调用
- **评测会写审计**：与真实问数一样落 `ask_audit_log`，审计身份是 `eval:<数据集名>`，
  可用 `WHERE username LIKE 'eval:%'` 过滤掉
